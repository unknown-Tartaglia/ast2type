# 类型推导与迁移实验阶段总结

本文按当前三项任务整理已有工作：选择适合展示编译通过率的数据、测试 TS 擦除后的迁移、
测试可控 JS 项目的直接推导与迁移，并记录人工检查发现的迁移流程问题。

## 1. 当前结论

| 任务 | 当前结果 | 结论 |
|---|---|---|
| 选择数据 | TypeWeaver 全量 245 包；条件子集 136 包 | 全量用于公平主结果，条件子集可展示较高通过率 |
| TS 迁移 | 4 个依赖可恢复项目，Raw 2151 条错误，项目级 Fix 后 893 条 | 错误下降 58.5%，但仍为 0/4 整项目通过 |
| 可控 JS 迁移 | 排除 bundle 后 7 个文件，Raw 与 Fix 均为 4/7 通过 | 3 个干净成功样例稳定通过，2 个样例暴露类型过窄问题 |
| 人工检查 | 已发现环境、文件隔离、类型渲染、无用代码和函数参数数量等问题 | 需要把类型 Auto-fix 与迁移规范化分开处理 |

## 2. 数据选择与高通过率结果

### 2.1 当前统一复检的全量结果

TypeWeaver `top1k-typed-nodeps-es6` 当前有效数据为 245 个包。全量结果应作为正式主结果，
因为它不根据某一种方法的成败筛选样本。除 LambdaNet 外，下表中的方法都使用 TypeScript
5.9.3 和同一组编译参数重新检查；LambdaNet 因为没有保留下来可重新编译的迁移后 TS
源文件，只能标为不可复检，其历史结果单独列在下一节。

| 方案 | 全量 TypeCheck | 通过率 | Accuracy | AnyRate |
|---|---:|---:|---:|---:|
| TS 推断基线 | 108/241 | 44.8% | 31.0% | 34.5% |
| DeepTyper | 54/226 | 23.9% | 50.0% | 30.0% |
| LambdaNet | 不可复检 | - | - | - |
| InCoder | 55/245 | 22.4% | 52.2% | 23.3% |
| SantaCoder | 76/245 | 31.0% | 54.9% | 26.8% |
| 纯 LLM | 96/229 | 41.9% | 72.6% | 5.2% |
| AST 标准，无 Fix | 95/245 | 38.8% | 15.7% | 42.9% |
| AST 标准，Auto-fix | 112/245 | 45.7% | 14.6% | 43.4% |
| AST Agent，无 Fix | 77/243 | 31.7% | 58.3% | 19.1% |
| AST Agent，Auto-fix | 94/243 | 38.7% | 53.1% | 22.1% |

标准模式 Auto-fix 的全量通过率最高，为 45.7%，但 Accuracy 较低且 AnyRate 较高。
因此，高编译通过率不能单独代表类型推导质量，正式结果仍需同时报告 Accuracy 和 AnyRate。

### 2.2 TypeWeaver 历史全方法结果

下面是 TypeWeaver 已有 `typecheck.*.csv` 中保存的结果。它包含 LambdaNet 和旧 Pipeline，
但来自当时的 TypeWeaver 编译环境，不是本次 TypeScript 5.9.3 统一复检，不能和上一张表的

| 方案 | 历史 TypeCheck | 通过率 | 覆盖 | 历史评测输入 |
|---|---:|---:|---:|---|
| TS 推断基线 | 112/241 | 46.5% | 241/245 | 原始 JS |
| DeepTyper | 54/226 | 23.9% | 226/245 | 预测结果织入后生成的 TS |
| LambdaNet | 24/213 | 11.3% | 213/245 | 预测结果织入后生成的 TS |
| InCoder | 56/245 | 22.9% | 245/245 | InCoder 生成的 TS |
| SantaCoder | 77/245 | 31.4% | 245/245 | SantaCoder 生成的 TS |
| 纯 LLM | 52/229 | 22.7% | 229/245 | LLM 生成的 TS |
| 旧 Pipeline | 92/222 | 41.4% | 222/245 | 旧 Pipeline 生成并处理后的 TS |

LambdaNet 历史检查目录中有 24 个 `.out` 和 189 个 `.err`，因此得到 `24/213`。当前只保留

LambdaNet 迁移的情况下得到可信的 TypeScript 5.9.3 结果。旧 Pipeline 的处理范围也不只
包含类型降级，因此只作为历史参考，不放进当前方法的正式主表。

### 2.3 编译通过率如何得到

所有编译通过率都以“包”为单位，而不是以单个文件为单位：一个包内的输入文件由同一次
`tsc` 调用检查，只要任意文件还有编译错误，整个包就记为失败。表中的通过率等于
“编译通过包数 / 该方法具有有效输入的包数”；缺少生成结果的包通过覆盖率另行反映。

| 方法 | 送入编译器的内容 | 编译通过的判定 |
|---|---|---|
| TS 推断基线 | 原始 `.js`，额外开启 `--allowJs --checkJs` | 整包 `tsc` 退出码为 0 |
| DeepTyper | DeepTyper 预测 CSV 经 TypeWeaver 织入得到的 `.ts` | 整包生成的 TS 全部通过 |
| LambdaNet | LambdaNet 预测经 TypeWeaver 织入得到的 `.ts` | 历史 `.out` 为通过、`.err` 为失败；当前无 TS 源文件可重跑 |
| InCoder / SantaCoder | 对应模型已经生成的 `.ts` | 整包生成的 TS 全部通过 |
| 纯 LLM | 已保存的 LLM 迁移 `.ts`，本次没有重新调用模型 | 整包生成的 TS 全部通过 |
| AST 标准 / Agent | 当前 Pipeline 将推导类型写回后得到的 `.ts` | 整包生成的 TS 全部通过 |
| AST Auto-fix | 在对应 Raw TS 上按诊断定位类型，并把相关类型降级为 `any` | Fix 后用相同编译器再次整包检查 |

历史结果由 TypeWeaver 对每个包运行一次编译：成功写为 `baseline-checked/<包>.out`，失败写为
`<包>.err`，再由 `summarize_results.py` 汇总成 `typecheck.<方法>.csv`。这些 CSV 没有记录
当时 TypeScript 的准确版本，因此报告时统一标为“历史 TypeWeaver 环境”。

当前统一复检不读取历史 `.out/.err` 判定，而是从各方法保留的源文件重新运行 TypeScript
5.9.3。除 TS 推断基线收集 `.js` 外，其余方法收集整包的 `.ts/.tsx/.mts/.cts`，排除
`.d.ts`、`.git` 和 `node_modules`，使用同一组模块、目标版本和声明生成参数。退出码为 0
且没有诊断才记为 PASS；不自动重试，也不把部分成功生成的声明计为通过。

## 3. TS 数据集迁移

### 3.1 测试方法

TS 实验先擦除原项目中的类型标注，再运行 ast2type 推导，将推导结果写回擦除后的 TS，
最后使用项目自己的依赖、`tsconfig` 和 TypeScript 版本编译。Ground Truth、Raw 和
Auto-fix 使用完全相同的项目环境。

`personal` 缺少私有包和上层 monorepo 文件，不能恢复真实编译环境，因此不纳入正式统计。
保留的项目为 `mapcn`、`vue`、`turbolinks` 和 `skills`。

### 3.2 类型写回情况

| 项目 | 原类型位置 | 推导命中 | 语法回退 | 未写回 |
|---|---:|---:|---:|---:|
| mapcn | 413 | 43 | 304 | 66 |
| vue | 4624 | 232 | 1777 | 2615 |
| turbolinks | 392 | 2 | 27 | 363 |
| skills | 976 | 88 | 240 | 648 |
| **合计** | **6405** | **365** | **2348** | **3692** |

直接由类型图命中的位置只有 365 个，占 5.7%；57.6% 的原类型位置没有写回。这解释了
严格模式下大量参数、变量、成员和返回值隐式 `any` 错误。语法回退主要用于索引签名、
属性等无法直接从图中获得类型但又必须保留 TS 语法的位置。

### 3.3 编译结果

| 项目 | Ground Truth | Raw 错误 | 项目级 Auto-fix | 错误下降 |
|---|---:|---:|---:|---:|
| mapcn | 通过 | 134 | 38 | 71.6% |
| vue | 通过 | 667 | 401 | 39.9% |
| turbolinks | 通过 | 384 | 131 | 65.9% |
| skills | 3 | 966 | 323 | 66.6% |
| **合计** | **3/4 通过** | **2151** | **893** | **58.5%** |

项目级 Auto-fix 共将 861 个可定位类型位置降级为 `any`。它基本清除了参数隐式 `any`
和错误属性类型，但四个迁移项目仍未整项目通过。`skills` 的 Ground Truth 自身还有 3 条
错误，解释该项目时需要单独标记。

Fix 后主要剩余：未使用 import 和失效 `@ts-expect-error`、变量/成员/返回值隐式
`any`、无效的 `array/function` 类型名，以及索引访问和 `unknown` 错误。前两类中的一部分
可以继续通过迁移规范化处理，但不都适合放入“只把报错类型改成 `any`”的 Auto-fix。

## 4. 可控 JS 项目迁移

### 4.1 样本选择

`tests/basic` 中共有 8 个 JS 文件。`bundle_demo.js` 是 865 行的打包产物，依赖虚拟模块、
`__d` 运行时和外部模块，不属于可控的简单 JS，因此从主要结论中排除。其余 7 个文件均可
直接由 Node.js 执行，编译评测按单文件进行，避免不同脚本间的全局变量重名。

| 文件 | 原始 JS checkJs | Raw TS | Auto-fix TS | 说明 |
|---|---:|---:|---:|---|
| large_object | 通过 | 通过 | 通过 | 无函数类型写回，稳定样例 |
| test_arg | 通过 | 通过 | 通过 | 参数和返回类型写回成功 |
| use_before_define | 通过 | 通过 | 通过 | 互相调用函数可正常迁移 |
| fail | 2 条错误 | 通过 | 通过 | 动态对象经 `any` 标注后通过 |
| deadlock | 通过 | 3 条错误 | 1 条错误 | 字面量结构类型推导过窄 |
| zjc-sample | 通过 | 1 条错误 | 1 条错误 | 参数结构包含不必要的具体字面量和构造器 |
| demo_a | 1 条错误 | 1 条错误 | 1 条错误 | 原 JS 的动态数组属性本来就无法通过 checkJs |
| **合计** | **5/7，3 条错误** | **4/7，5 条错误** | **4/7，3 条错误** |  |

如果需要一个稳定、可解释且高通过率的小展示集，可以选择 `large_object`、`test_arg` 和
`use_before_define`，三者在原始 checkJs、Raw 迁移和 Auto-fix 后均为 3/3 通过。
`fail` 可作为“动态 JS 通过宽化后迁移成功”的正面案例；`deadlock` 和 `zjc-sample` 适合
保留为类型过窄的回归案例。

完整 8 文件实验中，Auto-fix 将逐文件错误从 67 条降到 15 条，但通过数仍为 4/8。
其中 `bundle_demo` 一项就从 62 条降到 12 条，说明它会明显主导总错误数，不适合放入
简单项目的主要统计。

## 5. 人工检查发现的可修复迁移问题

除了类型值本身，当前还发现以下迁移或评测流程问题：

| 问题 | 现象 | 建议处理位置 |
|---|---|---|
| 项目依赖和编译配置缺失 | 统一参数下 Ground Truth 也失败；恢复项目环境后 3/4 通过 | 评测环境准备 |
| 独立脚本被作为同一全局程序编译 | `basic` 整目录比逐文件多出函数和变量重名错误 | 数据集/编译单元划分 |
| bundle 虚拟模块无法映射回源码 | 75 个目标中有 57 个是虚拟模块 `missing-file` | AST 路径映射或排除 bundle |
| 无效类型名 | `any[]`、函数类型被写成 `array`、`function` | 类型渲染与写回阶段 |
| 类型擦除后遗留无用代码 | 类型 import 变为未使用，`@ts-expect-error` 失效 | 独立迁移清理阶段 |
| JS 调用参数数量宽松 | JS 允许多传参数，生成固定 TS 签名后可能出现参数数量不匹配 | 函数签名规范化阶段 |
| Node/框架运行时全局量缺失 | bundle 中的 `__d`、私有模块或框架全局无法解析 | 依赖 shim 或排除不可控样本 |

这些问题不应全部塞入 Auto-fix。建议继续保持以下边界：

- Auto-fix：只根据编译诊断定位类型位置，并将高风险类型降级为 `any`；
- 迁移规范化：处理无效类型名、函数参数数量、脚本模块隔离和必要的无用代码清理；
- 环境准备：恢复依赖、项目 tsconfig、运行时全局声明和正确编译单元；
- 数据筛选：排除缺失私有环境、bundle 产物和 Ground Truth 本身不可编译的样本。

## 6. 下一步建议

1. 用 136 包可编译条件子集展示较高通过率，同时保留 245 包全量结果作为正式主表。
2. TS 迁移优先修复 `array/function` 类型渲染，以及变量、成员和返回类型的隐式 `any`。
3. 在 `large_object/test_arg/use_before_define` 上建立 3/3 的可控 JS 成功回归集。
4. 将 `fail/deadlock/zjc-sample` 建成正面与负面人工案例，记录迁移前后源码和诊断变化。
5. 后续分别报告生成成功率、逐文件通过率、整项目通过率和错误数量，不再只看单一 PASS。
